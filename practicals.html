ICA PRACTICAL 01 · SMALL PROJECT: SHOPEASY

ShopEasy — track, place, edit and cancel an order (GET, POST, PUT, DELETE)

1. Aim

To design one common HTML page and the Java servlets that search an order (GET), place an order (POST), change the delivery city (PUT) and cancel (DELETE), and to prove GET versus POST from the address bar (YouTube search versus YouTube comment).

2. Problem statement

Amazon forgets nothing you typed only because HTTP methods do different jobs. A static HTML page cannot search an order, cannot save a checkout without putting data in the URL, and cannot update or cancel. Write one HTML file that contains every form for this practical. Java may be more than one class.

  • GET tracks order roll 101 (like Amazon Track). Query may appear as ?roll=101.
  • POST places the order (name, roll, city) in the request body (like Checkout). Address bar stays /httpmethods.
  • PUT changes only the delivery city (like Edit address).
  • DELETE cancels the order (like Cancel order). A later GET must not find it.
  • On the same HTML, a YouTube search form uses GET (/getpostdiff?q=Java) and a comment form uses POST (text not in the URL).

Submit one HTML, complete Java (HttpMethodsServlet and GetPostDiffServlet) and complete web.xml. Do not write a second HTML file for GET versus POST.

3. Objectives

  • To override doGet, doPost, doPut, doDelete, doOptions and doTrace.
  • To prove from the address bar that GET data travels in the URL and POST data travels in the body.
  • To map one URL to many HTTP methods using web.xml.
4. Software required: JDK 17+ · Apache Tomcat 11.0.24 · Jakarta EE 11 · this web application · web browser.

5. Theory (copy into the journal — functions, syntax, use)

HTTP is the language between the browser and Tomcat. Every request has a method (verb). Class HttpServlet gives one Java method for each verb. You override the methods you need. The browser never runs this Java. Tomcat runs it and sends HTML back.

USE GET to search or open a page (data may sit in the URL). USE POST to save a form (data sits in the body; password must use POST). USE PUT to update (this lab: city). USE DELETE to remove. HTML forms can send only GET and POST. PUT and DELETE need fetch or Postman.

6. Real-life examples

  • GET — Amazon Track order, Flipkart search, Google search, YouTube search, IRCTC PNR lookup. Data can sit in the URL.
  • POST — Amazon Checkout, Gmail Send, Instagram comment, WhatsApp Web login, UPI PIN. Data stays in the body. Never put a password in GET.
  • PUT — Amazon Edit delivery city, Google Maps save home address, changing only one field of a saved record.
  • DELETE — Amazon Cancel order, YouTube remove a video from Watch later, emptying the cart.
  • OPTIONS — “What can I do at this window?” (Allow header). TRACE — debug echo; Tomcat 11 may block it.

7. Algorithm

  1. Browser sends an HTTP method to /httpmethods.
  2. Tomcat reads web.xml and calls the matching doXxx method.
  3. GET: read roll; if it matches the saved record, print name, roll, city.
  4. POST: store name, roll, city from the body; set exists = true.
  5. PUT: if roll matches, replace city only.
  6. DELETE: if roll matches, set exists = false.
  7. Print request.getMethod() and the saved record (or none).

8. Procedure

  1. Open the one Execute page for this practical (httpmethods.html).
  2. POST: place order Rahul / 101 / Solapur. Note the address bar (no name in the URL).
  3. GET: track 101. Confirm ?roll=101 in the URL.
  4. PUT: city Pune. GET again. DELETE: cancel 101. GET should not find it.
  5. On the same page: YouTube search GET (see ?q=Java) then comment POST (URL stays clean).

public class HttpMethodsServlet extends HttpServlet {
    static String name = "Rahul", roll = "101", city = "Solapur";
    static boolean exists = true;

    protected void doGet(HttpServletRequest req, HttpServletResponse res) throws Exception {
        String r = req.getParameter("roll");
        String msg = (exists && roll.equals(r)) ? "GET found " + r : "GET not found";
        show(req, res, msg);
    }
    protected void doPost(HttpServletRequest req, HttpServletResponse res) throws Exception {
        name = req.getParameter("name");
        roll = req.getParameter("roll");
        city = req.getParameter("city");
        exists = true;
        show(req, res, "POST saved (not in URL)");
    }
    protected void doPut(HttpServletRequest req, HttpServletResponse res) throws Exception {
        city = req.getParameter("city");
        show(req, res, "PUT city=" + city);
    }
    protected void doDelete(HttpServletRequest req, HttpServletResponse res) throws Exception {
        exists = false;
        show(req, res, "DELETE cancelled");
    }
    void show(HttpServletRequest req, HttpServletResponse res, String msg) throws Exception {
        res.setContentType("text/html");
        res.getWriter().println("<h2>" + req.getMethod() + "</h2><p>" + msg + "</p>");
    }
}

public class GetPostDiffServlet extends HttpServlet {
    protected void doGet(HttpServletRequest req, HttpServletResponse res) throws Exception {
        res.getWriter().println("GET search q=" + req.getParameter("q"));
    }
    protected void doPost(HttpServletRequest req, HttpServletResponse res) throws Exception {
        res.getWriter().println("POST review=" + req.getParameter("message"));
    }
}

13. Result

The servlet correctly distinguished HTTP methods. GET placed tracking data in the URL. POST stored checkout in the body. PUT updated city. DELETE cancelled the order. The same HTML also proved YouTube search (GET) versus comment (POST).

14. Conclusion

HTTP methods describe the job (read, write, update, remove). GET is suitable for search. POST is required for checkout, comments and passwords. One HTML page can hold every related form. One or more Java classes may sit behind that page.

15. Viva-voce

Q.1 Why cannot an HTML form send PUT?
A. The HTML specification allows form methods GET and POST only. PUT needs fetch, Postman or curl.

Q.2 Does getParameter work for both GET and POST?
A. Yes. Only the travel path of the data is different.

Q.3 Why is GET wrong for a password?
A. The password would appear in the URL, history and server logs.

ICA PRACTICAL 02 · SMALL PROJECT: WATCHTUBE

WatchTube — video views (lifecycle) and channel stamp (ServletConfig vs ServletContext)

1. Aim

To prove on one HTML page that Tomcat calls init once and service on every refresh (YouTube view count), and that a shared store name (ServletContext) is different from this counter’s clerk name (ServletConfig).

2. Problem statement

People think a new servlet object is created on every refresh. Prove the opposite like a YouTube video: the page is opened once (init), every replay/refresh is another view (service). Use LifecycleServlet (/lifecycle) with <load-on-startup>1</load-on-startup>.

Amazon prints the same store name on every receipt (ServletContext / context-param name collegeName in this lab). The clerk name on this counter is private (ServletConfig / init-param author). Put both forms on the same HTML. A second Java class ConfigContextServlet is allowed. Do not write a second HTML file.

3. Objectives

  • To override init(ServletConfig), service, doGet and destroy, always calling the matching super method.
  • To read getServletContext().getInitParameter and getServletConfig().getInitParameter.
4. Software required: same stack as Practical 1.

5. Theory (copy into the journal — functions, syntax, use)

Tomcat owns the servlet object. It calls init once (YouTube opens the video player), then reuses the object. Every refresh calls service then doGet/doPost (one more view). destroy runs when you undeploy; that message is on the Tomcat console, not in the browser.

ServletContext is the Amazon store name on every receipt (shared context-param). ServletConfig is this counter’s clerk stamp (private init-param). Both are read with getInitParameter(name). The object you call it on decides which XML you read.

getServletContext().getInitParametergetServletContext().getInitParameter("collegeName")Amazon store name (shared). Another servlet can read this too.

6. Real-life examples

  • init once — YouTube player loads once when you open the video. Instagram app starts once, not on every like.
  • service many times — Every refresh, like, or comment is a new request. View count goes 1, 2, 3… init stays 1.
  • destroy once — Closing the tab is not destroy. Destroy is Tomcat undeploy / stop — like shutting the cinema, not leaving your seat.
  • ServletContext — Amazon store name, Flipkart warehouse code, IRCTC “Indian Railways” — shared by every page of the site.
  • ServletConfig — This video’s author, this help-desk clerk, this counter’s language — only this servlet reads it.

7. Algorithm (lifecycle)

  1. Call super.init(config) and increment initCount.
  2. On each request increment serviceCount and call super.service.
  3. doGet prints both counters. destroy prints on the console only.

8. Procedure

  1. Open the one Execute page (lifecycle.html).
  2. Open the view counter (GET) five times. init stays 1. service grows.
  3. On the same page, open the store stamp. Copy store name (context) and clerk (config).
  4. Write: which values would a second servlet still see?

10. Medium Java (two classes)

public class LifecycleServlet extends HttpServlet {
    static int initCount = 0, serviceCount = 0;

    public void init(ServletConfig config) throws ServletException {
        super.init(config);
        initCount++;                         // once per load
    }
    protected void service(HttpServletRequest req, HttpServletResponse res)
            throws ServletException, IOException {
        serviceCount++;                      // every request
        super.service(req, res);
    }
    protected void doGet(HttpServletRequest req, HttpServletResponse res) throws Exception {
        res.getWriter().println("init=" + initCount + " service=" + serviceCount);
    }
    public void destroy() { System.out.println("destroy"); }
}

public class ConfigContextServlet extends HttpServlet {
    protected void doGet(HttpServletRequest req, HttpServletResponse res) throws Exception {
        String store  = getServletContext().getInitParameter("collegeName"); // shared
        String author = getServletConfig().getInitParameter("author");       // this servlet
        res.getWriter().println("store=" + store + " author=" + author);
    }
}

ICA PRACTICAL 03 · SMALL PROJECT: MYMAIL + PAYNOW

MyMail + PayNow — open mail (forward), pay (redirect), page with footer (include)

1. Aim

To implement, on one HTML page, server-side forward (Gmail stays in the same tab), client-side redirect (Amazon Pay changes the URL), and to state when include is used (wrong password + form).

2. Problem statement

Gmail opens a mail inside the same tab — the address bar does not change. Amazon Pay sends the browser to a bank URL — the address bar changes. Write one HTML with both forms. Java needs three classes: ForwardServlet, RedirectServlet, TargetServlet. Include is the third technique: paste an error line and the login form together (used in Practical 4). Do not write a separate HTML for redirect.

3. Objectives

  • To use getRequestDispatcher("/target").forward(request, response).
  • To use response.sendRedirect("target?...") and observe HTTP 302.
  • To explain that request attributes survive forward and are lost after redirect.
4. Software required: same stack as Practical 1.

5. Theory (copy into the journal — functions, syntax, use)

Forward is Gmail opening a mail in the same tab: same HTTP request, address bar stays /forward, setAttribute still works. Redirect is Amazon Pay: Tomcat sends 302, the browser opens a new request, the address bar changes, request attributes are lost. Include pastes another page into this response (wrong password + login form) and then your code continues.

6. Real-life examples

  • Forward — Gmail: after login you still see mail.gmail.com in the same tab. IRCTC: PNR check stays on the same URL while the server shows the result page. Address bar does not change.
  • Redirect — Amazon Pay / PhonePe / net-banking: after Pay now the URL must become the bank site. Instagram after login jumps to the home feed URL. Attributes from the first request are gone.
  • Include — Gmail wrong password: error line + login form on the same page. Flipkart “item out of stock” banner still shows the product page under it.

7. Algorithm

  1. Forward: read student, setAttribute message, getRequestDispatcher("/target").forward.
  2. Redirect: sendRedirect with query string (new GET). Do not rely on attributes.
  3. Target: if attribute present, it was forward; if query from= is present, it was redirect.

8. Procedure

  1. Open the one Run page (forward.html).
  2. Open mail (forward). Write the address bar. Did the page show PASS?
  3. Pay now (redirect). Write the new address bar. Are attributes gone?
  4. Run include. Address bar stays /include. A green line after the footer still runs.

public class ForwardServlet extends HttpServlet {
    protected void doPost(HttpServletRequest req, HttpServletResponse res) throws Exception {
        req.setAttribute("message", "PASS");           // same request bag

public class RedirectServlet extends HttpServlet {
    protected void doPost(HttpServletRequest req, HttpServletResponse res) throws Exception {
        res.sendRedirect("target?from=RedirectServlet&student=Rahul"); // 302, new GET
    }
}

public class TargetServlet extends HttpServlet {
    protected void doGet(HttpServletRequest req, HttpServletResponse res) throws Exception {
        Object msg = req.getAttribute("message");      // present after forward only
        String from = req.getParameter("from");        // present after redirect
        res.getWriter().println(msg != null ? "FORWARD " + msg : "REDIRECT from=" + from);
    }
    protected void doPost(HttpServletRequest req, HttpServletResponse res) throws Exception {
        doGet(req, res);                               // forward keeps POST
    }
}

ICA PRACTICAL 04 · SMALL PROJECT: MYMAIL ACCOUNT

MyMail account — Remember me, sign in, cookies off, hidden id, and full portal

1. Aim

To implement the four session-tracking techniques on one common HTML page and to join them in a mini Gmail-style portal (POST login, HttpSession, Remember-me cookie, forward on success, include on failure, logout). Several Java classes are required; extra HTML files are not.

2. Problem statement

HTTP is stateless: after one response Tomcat forgets the browser. YouTube still says Continue as Rahul, and Gmail still keeps you logged in, because we store something. Put every form on one HTML file. Implement and compare:

11. Result and conclusion

Result: Cookie remembered a display name and could be deleted. HttpSession kept the ERP login until invalidate. encodeURL carried extra ids (and session id if cookies were off). Hidden field survived forward. The portal joined POST, session, cookie, forward, include and logout.

Conclusion: Choose the technique by where the data must live. Cookie = browser, non-secret. Session = server, login. URL rewriting = cookies off. Hidden field = one extra POST, not a secret. A real portal uses session for identity and a cookie only for a display name.

12. Viva-voce

Q.1 Cookie versus HttpSession?
A. Cookie is client-side name=value. Session is a server-side map. Logout must invalidate the session.

Q.2 Why not store the password in a cookie or hidden field?
A. Both can be read on the client (storage or View Source).

Q.3 What two things must portal logout clear?
A. The HttpSession (invalidate) and the remember cookie (maxAge 0).

Q.4 Why forward on success and include on failure?
A. Forward shows Welcome on the same request (URL unchanged). Include reprints the form with an error.
