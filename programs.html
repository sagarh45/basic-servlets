Programs — Execute Online

This is a separate list from the ICA journal. Each program here is small, has its own real-life story from a different place — college office, hospital, bank, canteen, railway, library — and prints its answer on the same page in an Output box. Nothing jumps away, so you never lose the form.

A) One program for each theory chapter

Read the chapter, then run its program here. Different story, same concept.

Chapter 01 · College notice board

Story: a paper notice board never changes. The office wants a board that writes a fresh line by itself. That is why a servlet exists — Java builds the page, the browser only shows it.

HelloServlet · one doGet, one PrintWriter.

Execute Online Source Theory

Chapter 02 · Canteen counter — one window, many jobs

Story: one canteen window. “Show me the menu” is a different job from “take my order”. The window is one URL; the job is the HTTP method.

GetPostDemoServlet · same fields reach doGet and doPost.

Execute Online Source Theory

Chapter 03 · Weather site — the URL tells the secret

Story: you search a city on a weather site and the city sits in the address bar, so you can bookmark it. Type your email in the same style and everyone behind you can read it. That is why a password must never use GET.

DoGetDemo · watch the address bar after you submit.

Execute Online Source Theory

Chapter 04 · Temple footfall counter

Story: the gate counter is fixed once in the morning. Every person who walks in adds 1. Nobody buys a new counter per person. Tomcat does the same: init once, then one service per visitor.

CounterServlet · refresh and watch the count grow.

Execute Online Source Theory

Chapter 05 · Bank — this branch versus the whole bank

Story: the branch manager’s name belongs to one branch only (init-param → ServletConfig). The bank’s name is printed on every branch’s passbook (context-param → ServletContext). Two programs, one idea.

MyServlet reads the branch. ServletContextDemo reads the bank.

Branch (Config) Bank (Context) Source Theory

Chapter 06 · Hospital — same slip or a new counter?

Story: reception passes your slip to the doctor’s room without giving you a new token — that is forward, same request, URL unchanged. The ATM lobby instead tells you “go to counter 3” and you walk there yourself — that is redirect, new request, new URL.

IncludeServlet pastes a common hospital footer, then keeps printing — include returns, forward does not.

Include (footer) Redirect (new URL) Source Theory

Chapter 07 · Library card in your own pocket

Story: the library writes your name on a card and you keep it. Next visit you show the card instead of filling the form again. A cookie is that card: it lives in the browser, and the library can cancel it by asking for it back (setMaxAge(0)).

CookieDemo · write many names, read them all, delete one. Every name stays until you delete it.

Execute Online Source Theory

Chapter 08 · Railway cloakroom token

Story: the cloakroom keeps your bag and gives you a small token. The bag (your data) stays with the railway; you only carry the number. HttpSession works the same way — data sits in Tomcat memory, the browser carries only the session id. Losing the token, or the clerk closing the counter (invalidate()), ends it.

NotesSessionLogin, NotesSessionWelcome, NotesSessionLogout · login java / servlet.

Execute Online Source Theory

Chapter 09 · Capstone — card and token together

Story: a real site uses both. The library card (cookie) only remembers your name so the page can say hello. The cloakroom token (session) proves you are actually logged in. Logout must destroy both, or the next person on that computer walks in as you.

CapstoneLogin, CapstoneWelcome, CapstoneLogout · forward on success, include on wrong password.

Execute Online Source Theory
