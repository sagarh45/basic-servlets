2. HTTP Methods: GET, POST, PUT, DELETE, TRACE, OPTIONS

Theory Lab Setup Index
Verified for Apache Tomcat 11.0.24 (Jakarta EE 11 / Servlet 6.1) + JDK 17+
Every program uses jakarta.servlet.* only. See Lab Setup.

This page is theory only: meaning, real-life examples, diagrams, functions (syntax + use + example) and complete code. Copy the journal problem statement from the ICA Practicals tab or from the program Source page.

A) Concept in simple English

A hospital keeps one current patient file (name, id, city). Staff do different jobs on that same file: search, register, update city, remove, ask which jobs are allowed, and (rarely) echo a request for debugging. HTTP already has a verb for each of those jobs. You must not invent six different URLs; you use one URL /httpmethods and six methods.

Picture it from daily life

One-line rule: One hospital counter (/httpmethods). Six different jobs. The job name is the HTTP method, not a new URL.

The story (one counter, many verbs)

The OPD has one window. Patients do not go to six different rooms. They stand at the same window and say what they want:

  1. GET — “Show me patient 101.” Search. Anyone can repeat the same question. The id is visible (like writing it on a token).
  2. POST — “Register this new patient.” Fill a form. The paper goes in an envelope (request body), not written on the token.
  3. PUT — “This patient moved to Pune. Keep id 101. Change only the city.” Update, do not create a second file.
  4. DELETE — “Discharge / remove this file.” Later search must say not found.
  5. OPTIONS — A new nurse asks “what jobs does this window do?” The answer is a list (Allow header). Nobody’s file is opened.
  6. TRACE — “Repeat what I just said” (debug echo). Real Tomcat often refuses this for security. That refusal is still the correct observation.

HTML forms in a browser can only say GET and POST. PUT / DELETE / OPTIONS / TRACE in this lab use the Execute buttons (fetch), like an internal slip, not the public form.

What you will see

After GET search, the address bar shows ?roll=101. After POST register, the address bar stays /httpmethods. Same servlet. Different verb. That is the whole chapter.

Easy mistake

Making six URLs (/get, /post, …). The syllabus point is one URL, six methods.

Real-life examples (short recap)

GET — Google / IRCTC PNR search

You search a PNR. The URL becomes /httpmethods?roll=101. Anyone with that link can repeat the search. That is GET: read, bookmarkable, visible in the address bar.

POST — Amazon checkout / Gmail login

You fill name, id, city and click Save. Details must not hang in the address bar. That is POST: write, body not URL.

PUT — change only the city

The person moved from Solapur to Pune. The id stays 101; only city changes. PUT means “replace this field of the existing resource”, not “create a second person”.

DELETE — remove the file

The hospital removes id 101. Later GET for 101 must say not found.

OPTIONS — “what can this counter do?”

OPTIONS answers with the Allow list. It does not open a patient file.

TRACE — debug mirror

A network engineer asks the server to echo the request. Production Tomcat often disables TRACE (Cross-Site Tracing). In the lab, if TRACE fails, write that observation; it is still the correct theory.

What is an HTTP method? (read this first)

HTTP is the language between the browser and Tomcat. Every request has a method (a verb such as GET or POST). The method tells the server what the client wants to do with a resource (here: one student record).

Class HttpServlet already has one Java method for each HTTP method: doGet, doPost, doPut, doDelete, doOptions, doTrace. You override only the methods you need. Tomcat reads the incoming HTTP method and calls the matching doXxx. If you did not override it, Tomcat usually answers HTTP 405 Method Not Allowed.

HTML forms can send only GET and POST. PUT, DELETE, OPTIONS and TRACE are sent in this lab with a small JavaScript fetch() button (or with Postman / curl).

Live check: request.getMethod() returns the method name as a String (GET, POST, ...).

1. GET — search / read (Java: doGet)

Simple meaning: GET means please show me this data. It is a read. It should not create a new student.

How it works: The browser puts extra data in the address bar as a query string. Example: /httpmethods?roll=101. Anyone who copies the URL can repeat the same search. Refresh and bookmarks also use GET.

Lab example: Fill roll 101 and click Search student (GET). The servlet looks up the saved student. If the roll matches, it shows name, roll and city. If not, it says the student was not found. After submit, look at the address bar: ?roll=101 is visible.

Choose GET when you open a page, click a link, refresh, search, or want a URL that can be bookmarked.

Do not choose GET when you send a password, a large form, or any data that must stay hidden. GET data appears in the URL, in history, and in server logs.

HTML: <form method="get" action="httpmethods"> or a normal link <a href="httpmethods?roll=101">.

@Override

2. POST — fill a form and save (Java: doPost)

Simple meaning: POST means please accept this form and save it. It is a write. In the lab it registers a new student (name, roll, city) in server memory.

How it works: The browser puts the fields in the request body, not in the address bar. After submit the URL usually stays the same. You cannot see name or password in the URL. That is why login and register use POST.

Lab example (student office — do not mix with the sample below): On Execute, fill Name / Roll / City and click Register student (POST). That office form is only three boxes. It is a different page from the sample registration form.

Choose POST when the student fills a form: register, login, feedback, any data that should not sit in the URL.

Do not choose POST when you only want to open or bookmark a search. POST is not meant to be a shareable link. Refresh after POST may ask the browser to send the form again.

3. PUT — update an existing record (Java: doPut)

Simple meaning: PUT means please replace this resource with the new data. The record must already exist. In the lab, PUT changes the city of the saved student.

How it works: PUT is idempotent: sending the same update twice should leave the same final city. It is used in REST APIs. A normal HTML <form> cannot send PUT (browsers only submit GET or POST). This lab uses a button that calls JavaScript fetch(..., {method:'PUT'}).

Lab example: First register with POST. Then type the same roll and a new city (example Pune) and click Update city (PUT). The name and roll stay. Only the city is replaced. If the roll does not match, PUT refuses.

Choose PUT when you update / replace a record that already exists (REST update).

Do not choose PUT when you create the first record (that is POST), or when you only have a normal HTML form without JavaScript / Postman.

Syntax

@Override
protected void doPut(HttpServletRequest request, HttpServletResponse response)
        throws ServletException, IOException {

    String city = request.getParameter("city");
    // If roll matches the saved student, replace the city. Do not insert a new student.
}

4. DELETE — remove the record (Java: doDelete)

Simple meaning: DELETE means please remove this resource. After a successful DELETE, GET search for that roll should not find the student.

How it works: Like PUT, a normal HTML form cannot send DELETE. The Execute page uses fetch(..., {method:'DELETE'}) with the roll number.

Lab example: Type roll 101 and click Remove student (DELETE). The saved record is cleared. Search GET for 101 then says not found. Register with POST if you need the student again.

Choose DELETE when you remove a resource (REST delete).

Do not choose DELETE from a plain college HTML form. If the browser can only submit a form, teachers often use POST with a hidden field such as action=delete. In this lab we send a real DELETE so you see doDelete.

5. OPTIONS — ask which methods are allowed (Java: doOptions)

Simple meaning (remember this): OPTIONS is not a student job. It is only a question: "On this URL, which HTTP methods are allowed?" The server answers with a list of verbs. It does not search a roll, register a name, change a city, or delete a record.

College-office picture: You walk to the student office counter and ask: "What can I do at this window?" The clerk does not open Rahul's file. The clerk only points to the notice board: Search (GET), Register (POST), Update city (PUT), Remove (DELETE), Ask this list (OPTIONS), Debug (TRACE). That notice board is the HTTP header named Allow. OPTIONS = reading the notice board. GET = opening one student's file.

How it works, step by step:

  1. The browser (or Postman) sends HTTP method OPTIONS to the same URL /httpmethods.
  2. Tomcat sees OPTIONS and calls doOptions (not doGet).
  3. Your Java code sets a response header: Allow: GET, POST, PUT, DELETE, TRACE, OPTIONS.
  4. The important answer is in that header. The HTML page is only for the student to read in the lab.
  5. The saved student (Rahul / 101 / Solapur) is not changed.

What is the Allow header? HTTP has two parts: headers (small labels) and body (the HTML page). Allow is a header. It is a comma-separated list of method names. A program (browser, Postman, another website) can read Allow without looking at the HTML. In Chrome: Execute the OPTIONS button → press F12 → Network → click the httpmethods row → Headers → Response Headers → find Allow.

Why can't a normal HTML form send OPTIONS? A form has only method="get" or method="post". There is no method="options" in HTML. So this lab uses a button and JavaScript fetch('/httpmethods', {method:'OPTIONS'}). You can also test with Postman: method = OPTIONS, URL = http://localhost:8080/basic-servlets/httpmethods.

CORS in one line (viva extra, not the main lab job): If website A wants to call a servlet on website B, the browser first sends OPTIONS ("preflight") to ask: is this call allowed? That is another use of OPTIONS. In this lab we only show the Allow list for the student office URL. You do not need CORS code to pass the practical.

Lab example: On Execute click Ask allowed methods (OPTIONS). You should see a teaching page plus request.getMethod() = OPTIONS. Then open Network tab and copy the Allow value into your journal. Compare: GET search still shows Rahul; OPTIONS did not search.

Choose OPTIONS when

  • a client / API tool must discover which methods this URL supports;
  • you are teaching doOptions and the Allow header;
  • (later in industry) a browser sends a CORS preflight.

Do not choose OPTIONS when

  • you want to open or bookmark a page → use GET;
  • you want to register / login → use POST;
  • you want to change city or remove the student → use PUT / DELETE.

6. TRACE — debug echo (Java: doTrace)

Simple meaning (remember this): TRACE means "send my request back to me, exactly as you received it." It is a debug mirror. The server echoes (repeats) the request. It is not search, not register, not update, not delete, and not the Allow list.

Easy picture: You shout a sentence into a valley. The echo comes back so you can hear what you shouted. TRACE is that echo for HTTP. You are not asking for Rahul's city. You are asking: "Tomcat, what request did you actually receive from me?" A teacher uses this to check if a proxy or firewall changed headers on the way.

How it is supposed to work:

  1. The client sends HTTP method TRACE to /httpmethods (again: no HTML form can do this).
  2. If the server allows TRACE, it copies the incoming request (method, URL, headers) into the response body.
  3. The client reads that copy. That is the echo. No student record is read or written.
  4. In Java, Tomcat would call doTrace only if TRACE is enabled.

Why Execute TRACE often fails (this is the important lab fact): TRACE can be misused. If a browser is tricked into sending TRACE, the echo might include cookies or Authorization headers. Attackers called this Cross-Site Tracing (XST). Because of that, Apache Tomcat turns TRACE OFF by default (Tomcat 11 included). So when the student clicks Debug TRACE, the browser may show an error, HTTP 405 Method Not Allowed, or a blocked connection. That is not a bug in your servlet. Write in the journal: Tomcat security blocked TRACE. Expected. Do not enable TRACE on a college production server just to make the button look successful.

Lab example: Click Debug TRACE on Execute.

  • If it runs: the page shows a teaching line and getMethod() = TRACE. Still no change to Rahul.
  • If it fails: copy the error. That is the correct Tomcat default. You still understand TRACE from this theory.

Choose TRACE only when

  • the syllabus asks you to name all HTTP methods including TRACE;
  • a teacher wants a demo that the method exists in HttpServlet.

Do not choose TRACE when

  • you need student data → GET / POST / PUT / DELETE;
  • you need the list of allowed methods → that is OPTIONS, not TRACE;
  • you are deploying a real website. Leave TRACE disabled.

File: HttpMethodsServlet.java. One in-memory student (static fields). Restarting Tomcat resets the record.

import java.io.IOException;                      // I/O exceptions from the writer
import java.io.PrintWriter;                      // Prints HTML to the browser
import jakarta.servlet.ServletException;         // Required on doXxx signatures
import jakarta.servlet.http.HttpServlet;         // Base class with doGet, doPost, ...
import jakarta.servlet.http.HttpServletRequest;  // Incoming method + parameters
import jakarta.servlet.http.HttpServletResponse; // Outgoing HTML + headers

public class HttpMethodsServlet extends HttpServlet {  // One office window, many verbs

    static String name = "Rahul";    // Demo student name kept in server memory
    static String roll = "101";      // Demo roll number
    static String city = "Solapur";  // Demo city
    static boolean exists = true;    // false after DELETE until a new POST

    @Override
    protected void doGet(HttpServletRequest request, HttpServletResponse response)
            throws ServletException, IOException {           // Tomcat calls this on HTTP GET
        String r = request.getParameter("roll");             // Read ?roll=101 from the URL
        String msg;                                          // Message we will print
        if (r == null || r.isEmpty()) {                      // No roll typed: just a view
            msg = "GET view";
        } else if (exists && roll.equals(r)) {               // Roll matches the saved file
            msg = "GET found roll " + r;
        } else {                                             // Wrong roll or already deleted
            msg = "GET roll not found: " + r;
        }
        show(request, response, msg);                        // Common HTML printer
    }

    @Override
    protected void doPost(HttpServletRequest request, HttpServletResponse response)
            throws ServletException, IOException {           // HTTP POST = register / save
        name = request.getParameter("name");                 // Body field name (not in URL)
        roll = request.getParameter("roll");                 // Body field roll
        city = request.getParameter("city");                 // Body field city
        exists = true;                                       // Record is alive again
        show(request, response, "POST saved (body, not URL)");
    }

    @Override
    protected void doPut(HttpServletRequest request, HttpServletResponse response)
            throws ServletException, IOException {           // HTTP PUT = update city
        String r = request.getParameter("roll");             // Which student
        String c = request.getParameter("city");             // New city
        if (exists && roll.equals(r)) {                      // Update only if roll matches
            city = c;
            show(request, response, "PUT updated city to " + city);
        } else {
            show(request, response, "PUT no matching roll");
        }
    }

    @Override
    protected void doDelete(HttpServletRequest request, HttpServletResponse response)
            throws ServletException, IOException {           // HTTP DELETE = remove record
        String r = request.getParameter("roll");
        if (exists && roll.equals(r)) {
            exists = false;                                  // Mark deleted (memory only)
            show(request, response, "DELETE removed roll " + r);
        } else {
            show(request, response, "DELETE no matching roll");
        }
    }

    @Override
    protected void doOptions(HttpServletRequest request, HttpServletResponse response)
            throws ServletException, IOException {           // HTTP OPTIONS = menu of verbs
        response.setHeader("Allow", "GET, POST, PUT, DELETE, TRACE, OPTIONS"); // Allow header
        show(request, response, "OPTIONS Allow header set");
    }

    @Override
    protected void doTrace(HttpServletRequest request, HttpServletResponse response)
            throws ServletException, IOException {           // HTTP TRACE = debug echo
        show(request, response, "TRACE debug (Tomcat may block this)");
    }

    private void show(HttpServletRequest request, HttpServletResponse response, String msg)
            throws IOException {                             // Shared HTML for every verb
        response.setContentType("text/html");                // Tell the browser: HTML body
        PrintWriter out = response.getWriter();              // Character writer
        out.println("<h2>request.getMethod() = " + request.getMethod() + "</h2>"); // Live verb
        out.println("<p>" + msg + "</p>");                   // Job-specific message
        if (exists) {
            out.println("<p>Saved: " + name + " / " + roll + " / " + city + "</p>");
        } else {
            out.println("<p>Saved: none</p>");
        }
        out.println("<p><a href='httpmethods.html'>Back</a></p>");
    }
}
